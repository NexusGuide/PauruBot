# بازگردانی نسخه (rollback) و سازگاری image با schema

> مرجع اجرایی SEC-F22. این سند می‌گوید یک نسخهٔ PauruBot روی کدام دیتابیس اجرا می‌شود، `pauru rollback` در هر حالت چه می‌کند و اگر کار خودکار ممکن نبود، چه باید کرد.

## قاعدهٔ سازگاری

migrationها فقط رو به جلو هستند و هیچ release‌ای schema را به عقب برنمی‌گرداند.

| وضعیت دیتابیس نسبت به release (`paurubot schema-status`) | کد خروج | نتیجه |
|---|---|---|
| `same`: revision دیتابیس همان head این release است | 0 | اجرا می‌شود |
| `older`: revision را می‌شناسد ولی قبل از head است | 3 | سرویس `migrate` آن را جلو می‌برد، سپس اجرا می‌شود |
| `newer`: revisionی که این release نمی‌شناسد (یک release جدیدتر migrate کرده) | 4 | **اجرا نمی‌شود**. `migrate` شکست می‌خورد و `/readyz` آماده نمی‌شود |
| `empty`: هنوز schemaای نیست | 5 | نصب تازه؛ `migrate` می‌سازد |
| دیتابیس در دسترس نیست | 6 | هیچ تصمیمی گرفته نمی‌شود |

نتیجه: اگر یک update حتی یک migration داشته باشد، release قبلی روی دیتابیس فعلی اجرا نمی‌شود. بازگردانی در این حالت یعنی **برگرداندن داده‌ها به backup پیش از update**، نه فقط عوض‌کردن image.

## update چه چیزی برای rollback ثبت می‌کند

`pauru update` پیش از هر تغییری:

1. با worker یک backup رمزگذاری‌شده می‌سازد. اگر backup شکست بخورد، update بدون هیچ تغییری متوقف می‌شود.
2. مسیر آن را در `.env` با نام `PAURUBOT_PREVIOUS_BACKUP` ثبت می‌کند، به‌همراه image و نسخهٔ قبلی (`PAURUBOT_PREVIOUS_IMAGE` و `PAURUBOT_PREVIOUS_VERSION`).
   پاک‌کردن نسخه‌های قدیمی پشتیبان (هر چند نسخه‌ای که در صفحهٔ پشتیبان‌گیری نگه داشته شود) این فایل را هرگز پاک نمی‌کند.
3. سپس release تازه را بالا می‌آورد. سرویس `migrate` پیش از هر سرویس دیگری schema را جلو می‌برد.

## `pauru rollback`

1. از **image قبلی** می‌پرسد که آیا روی دیتابیس فعلی اجرا می‌شود: `schema-status` با همان image.
2. **کد 0 یا 3:** فقط image را عوض می‌کند. داده دست نمی‌خورد.
3. **کد 4 (schema جلوتر رفته):**
   - backup ثبت‌شدهٔ پیش از update را با تاریخش نشان می‌دهد و اعلام می‌کند که **هرچه بعد از update نوشته شده از بین می‌رود**، سپس تأیید صریح می‌خواهد.
   - api، bot و worker را متوقف می‌کند، image قبلی را برمی‌گرداند و با **release قبلی** و نقش مالک (سرویس `migrate`) backup را restore می‌کند. restore در یک تراکنش انجام می‌شود.
   - اگر restore شکست بخورد، دیتابیس دست‌نخورده می‌ماند و release فعلی دوباره بالا می‌آید.
   - پس از موفقیت، `PAURUBOT_PREVIOUS_BACKUP` پاک می‌شود، چون آن backup مال updateای بود که برگردانده شد.
4. **هر حالت دیگری** (کد 6، backup ثبت‌نشده، یا لغو توسط اپراتور): **هیچ چیز تغییر نمی‌کند**.

rollback از **پنل مدیریت** (agent) فقط وقتی انجام می‌شود که داده تغییری لازم نداشته باشد. اگر restore لازم باشد، agent کاری نمی‌کند و پیام می‌دهد که `pauru rollback` باید روی خود سرور و با تأیید انسانی اجرا شود.

## پیش از تأیید restore در نظر بگیرید

- **پرداخت‌های بعد از update:** پرداختی که بعد از update در درگاه یا زنجیره انجام شده، پس از restore در دیتابیس نیست، ولی پول جابه‌جا شده است. فهرست پرداخت‌های آن بازه را از پنل درگاه یا کیف‌پول بگیرید و بعد از restore دستی تطبیق دهید (شارژ کیف‌پول، یا رسیدگی در صف پرداخت‌ها).
- **حساب‌های ساخته‌شده روی پنل:** سرویس‌هایی که بعد از update روی پنل ساخته شده‌اند، پس از restore در ربات نیستند ولی روی پنل می‌مانند. پیش از حذف یا تحویل دوباره، آن‌ها را با فهرست سفارش‌ها مقایسه کنید.
- اگر مشکلِ نسخهٔ تازه با یک update بعدی رفع‌شدنی است، update رو به جلو معمولاً از restore کم‌هزینه‌تر است.

## اگر backup ثبت نشده یا خودکار ممکن نیست

1. backupهای موجود را ببینید: `docker compose exec worker paurubot backups`. یکی را انتخاب کنید که **پیش از** update ساخته شده است.
2. image قبلی را در `.env` برگردانید (`PAURUBOT_IMAGE` و `PAURUBOT_VERSION` را با مقادیر `PAURUBOT_PREVIOUS_*` جابه‌جا کنید).
3. سرویس‌ها را متوقف کنید: `docker compose stop api bot worker`.
4. با سرویس migrate (نقش مالک) restore کنید:
   `docker compose run --rm --no-deps migrate restore /var/lib/paurubot/backups/<file>.pbak`
   برای backup بیرون از سرور، از `pauru restore /path/file.pbak` استفاده کنید.
5. سرویس‌ها را بالا بیاورید: `docker compose up -d`. سپس `paurubot schema-status` باید `state=same` بدهد و `pauru status` سالم باشد.

## برای نویسندگان migration

- migration را برگشت‌ناپذیر فرض کنید. rollback بدون restore فقط برای releaseهایی ممکن است که migration ندارند.
- هر migration پیش از ادغام باید در CI روی دیتابیس واقعی اجرا شود (مجموعهٔ آزمون همین کار را می‌کند). `downgrade` برای توسعه است، نه برای بازگردانی production.
